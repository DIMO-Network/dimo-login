# Flows and screens

Every screen of Login with DIMO, how a user gets there, what it signs and what the app is told. The app starts a flow with `entryState` (popup `AUTH_INIT` message, redirect query, or a `configurationId`/`configCID` configuration). Screens switch through `UIManagerContext.setUiState`; there is no router. Each one renders inside `AppShell` (top bar with Back, logo and language switcher; a sticky `ActionBar` for its buttons).

How the app is told, by transport:

| Transport      | What happens                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Popup          | `postMessage` to the opener. Messages that carry a token, signature or key (`*Response`) are addressed to the registered `redirectUri`'s origin; `READY`, the `*_DATA` requests, `DIMO_ERROR` and `logout` go to the opener's origin. The done screen's Back closes the popup.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Embed (iframe) | `postMessage` to the parent, same origin rule. Done screens hide Back and Cancel/Continue only post the message: the embedder navigates. Errors and cancels end on `TRANSACTION_CANCELLED`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Redirect       | The done screen's Back redirects to `redirectUri` with the same keys in the query (values are never `undefined`), plus the SDK's `dimoState` when it sent one. With `responseMode=fragment` (SDK `redirectResponseMode: 'fragment'`), the keys the SDK reads (`token`, `walletAddress`, `email`, `logout`) and `dimoState` go in the URL fragment instead, which browsers don't send to the app's server; what the app reads itself (`error`, `transactionHash`, `signature`, `sharedVehicles`, …) stays in the query, and so does `dimoState` when nothing goes in the fragment. A redirect URI that already has a `#` (a hash route) gets the query. `responseMode` is `query` (the default) or `fragment`; any other value is dropped. |

In popup and embed mode the page that opens or embeds the login must be on the redirect URI's origin; otherwise it shows "This page can't open this sign-in" (see `security-headers.md`, Cross-site requests).

The SDK turns `authResponse` messages into `onSuccess({ token, email?, sharedVehicles?, revokedVehicles?, extendedVehicles?, accountGranted? })`.

## Signing in

Reached first whenever there is no valid session: this app's token with at least an hour left (a quarter of its lifetime, for a token issued for less than four hours), and its stored user. A valid session skips it and goes to `entryState`, or for a plain login to `SUCCESS` (embedded, where `SUCCESS` has no Back, it continues as a fresh sign-in does: `EMAIL_CONSENT` if needed, then `authResponse`). `LOGOUT` runs with or without a session. After sign-in, the onboarding states (`ADD_VEHICLE`, `CONNECT_TESLA`, …) have no route of their own, so an app shouldn't start a flow on them.

**Account bar.** Every request screen after sign-in (`SUCCESS`, `EMAIL_CONSENT`, `VEHICLE_MANAGER`, `MANAGE_VEHICLE`, `ACCOUNT_MANAGER`, `SIGN_MESSAGE`, `ADVANCED_TRANSACTION`, `PROVISION_DEVELOPER_LICENSE`, `CONNECTED_APPS`) starts with a bar that says "Signed in as {email}" and offers "Use another account". That signs this app out inside the login (its token and stored user are cleared) and reopens the chooser; the app is not told and the login is not left. Signing in again: for a plain login the new sign-in goes through the email step if needed and then sends the new login to the app; for every other flow it returns to the screen the app asked for, as the new account. Embedded, the app that already received the first account's login receives a second one if the user switches and signs in again. The button is hidden while something is being signed. Switching does not end the first account's wallet session.

**Accounts and wallet sessions on this browser.** The chooser lists up to five accounts: those signed in on this browser, in any app, most recent first (`dimo_accounts`), and, when that list lacks it, the account this app last signed in as (`logged_email_<clientId>`, all that a browser upgraded from the build before the list knows). Each account has its own wallet session (`turnkey_session_<subOrganizationId>`): a passkey marker, or the email-code key with its expiry. A session stored before this change is not carried over. At every sign-in and removal, the sessions of accounts no longer listed and email-code keys past their expiry are deleted. Every sign-in, by passkey, code or a chosen account, starts the page's wallet signer afresh. When a screen needs to sign and the stored wallet session is gone (logged out or removed elsewhere, or a session from before this change), the user is sent to the chooser to sign in again; a signer still holding another account's session is started afresh. The login sent to the app is this tab's own token and account, which another tab of the same app may have switched; a token with less than a minute left is never sent: the screen opens the chooser instead, and signing in again returns to the request. Remembered accounts, and Log out ending the wallet session, hold in popup and redirect mode; embedded, the browser partitions storage by the embedding site, so each embedding site has its own list and wallet sessions. With `REACT_APP_SIGN_IN_NOTICE=true`, a sign-in by passkey or code as an account this list doesn't have yet (never a silent resume) tells the accounts API, with the token just made and a random key this browser keeps (`dimo_device_key`), which may then email the account about a sign-in on a new browser; nothing waits on it, and where storage is blocked nothing is sent.

**Asking for an account.** The app can send two optional parameters with its request (SDK `prompt`, `loginHint`: in the AUTH_INIT message, the redirect query, or a stored configuration). A value that isn't one of those below is dropped.

- `prompt=select_account` shows the sign-in screen with the account chooser even when a valid session exists; embedded, that session isn't posted to the app either. `prompt=login` does the same, and a click on a remembered account never signs in silently: the user passes the passkey or code step.
- `loginHint=<email>` (stored lowercase) names the account the app expects. A valid session for that account (its stored email compared ignoring case) is used as usual; one for another account is not. On the sign-in screen, a hint that matches a remembered account narrows the chooser to it plus "Use another account" (which opens an empty email field); a hint that matches none opens the email field pre-filled with it, with "Back to accounts" when there are remembered accounts. A hint never signs anyone in by itself.
- Nothing stored is cleared: a session that isn't used stays, and choosing its account can still sign in without a step (not under `prompt=login`). `entryState=LOGOUT` ignores both parameters.
- Both apply until someone signs in on the page, a valid session used at the start included, and are spent for the rest of the page after that: the account bar's "Use another account" opens the chooser with every remembered account (and its own "Use another account" an empty email field), and a chosen account may sign in silently again.
- A Google/Apple return is a new page load with the parameters restored from its saved flow, so they apply again until that sign-in completes. The sign-in screen shows its loader from the first render while the provider's code is exchanged, so the sign-in in progress goes on rather than offering the chooser again. A Tesla return restores neither: Tesla is connected after sign-in, so the session made before leaving is used.
- In redirect mode `loginHint` arrives in this page's URL. Once read it is removed from the address bar (other parameters and the hash stay) and kept in the page's history entry, so a reload, or Back to the page, still has it. Error reports never include it: in every URL Sentry records, the first page's included, its value reads `[Filtered]` (`dataCollection.urlQueryParams` in `src/sentryOptions.ts`). The hosting provider's request log still records the URL the page was opened with.
- An older SDK, or a hand-built link, that sends neither parameter behaves as before.

**Email sharing.** The app says what it wants with `emailRequest`: `none`, `optional` (the default) or `required`; the older `forceEmail=true` means `required`. The email is asked for after sign-in, as an item of the app's request: in the About you group of the share-vehicles and share-documents cards, or on `EMAIL_CONSENT` for a plain login (shown only while a required email isn't shared, or an optional one was never answered). The answer is stored per app and account (`email_granted_<clientId>_<email>`) when the user approves or continues, never on Cancel; a grant stored before that keying moves to the account it belonged to, and is never handed to another account. `email` is sent only when it's shared and the app didn't ask for `none`. With `required`, Cancel before the email is shared ends with `error: 'User declined to share their email'`, so the app never gets a login without it; Stop sharing still reports the revocation. A Google/Apple sign-in leaves for the provider with the flow saved in sessionStorage under a nonce (`flowRef` in OAuth `state`) and restored on return. A return whose `flowRef` this tab didn't save shows "This sign-in can't be finished here" and its code is never exchanged.

## Connected apps (`entryState=CONNECTED_APPS`)

Off unless the login is built with `REACT_APP_CONNECTED_APPS=true`; until then the entry state is dropped as unknown, so the request is a plain sign-in. It needs a signed-in account, as every flow does. Embedded, it is refused before sign-in ("Open this page in its own window"): the browser keeps a separate store per embedding site, and this page ends access. No parameter but `entryState` is used, so an app can't preselect what to stop.

## Language

`language` (`en`, `ja`, `ja-JP`…) can come from the app (SDK option or button prop, redirect query, configuration). The user's pick in the switcher wins and is stored per app. Without either, a Japanese browser or the `Asia/Tokyo` time zone gets Japanese. Protocol strings above (error reasons, payload keys, event types) stay English. See `i18n.md`.
